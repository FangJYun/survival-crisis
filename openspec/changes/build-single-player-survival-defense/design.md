# Design

## Context

动机与能力范围见 proposal.md。实际检查结果：项目仅有 openspec/config.yaml、空规格目录和归档占位文件，无游戏源码、包清单、场景、资产、自动化测试或已有能力规格。OpenSpec 根路径由 context 命令确认指向当前项目，当前无其他变更。

Node.js v26.10.0 已可用，但这不等于 Cocos 工具链兼容性已经验证；标准应用目录和 PATH 快速检查未发现 Cocos 或微信开发者工具，不能据此断言整台机器没有安装。实施前需确认实际路径、兼容 Node 版本、编辑器补丁版本和测试 AppID。只记录工具路径及公开 AppID，不将密钥写入配置或日志。

本设计覆盖完整首版，以六个阶段逐步交付，不将第一晚试玩等同于所有玩法完成。用户确认的规则优先于讨论中的旧建议：装备永久损失，不生成遗物；额外主动技能本局最多学习两种，而非学习任意数量再选择两个。

## Goals / Non-Goals

**Goals:**
- 用独立于场景节点的规则状态支撑战斗、动态建筑、成长和本地恢复。
- 把死亡、物品交易、迁塔及塔终局组合成可测试、可恢复的状态转换。
- 在真实微信运行环境中验证操控、加载、内存与夜袭性能。
- 平衡数值与内容数据可配置；通过小内容量先验证体验，再补齐完整首版。

**Non-Goals:**
- 不实现联机同步、权威服务器、防篡改经济、账号和跨设备存档。
- 不追求复杂物理、全地图实时生态、无限世界或大型通用 ECS 框架。
- 不将自动生成的素材直接视为通过美术验收，不承诺尚未实测的帧率或兼容性。

## Decisions

### 1. 引擎、工程与模块边界

选择 Cocos Creator 3.8 LTS 的经构建验证的稳定补丁版、TypeScript 与横屏 2D。先建立官方可识别工程，在微信开发者工具运行空场景，再实现游戏。版本选定后锁定项目编辑器版本和依赖锁文件，不使用浮动 latest。

相比 Unity／团结引擎，本项目没有既有 C# 资产与复杂 3D 需求；相比裸 Canvas／Phaser，选择带场景、UI、动画和微信构建流程的引擎减少适配工作。LayaAir 可替代，但当前没有团队既有栈优势，不维护双引擎实现。

拟定工程边界（尚未创建）：

| 路径 | 责任 |
| --- | --- |
| assets/scripts/domain/ | 类型、时钟、战斗、AI、物品、采集、建筑、成长、终局规则；不导入 cc 或 wx |
| assets/scripts/application/ | 固定步调度、命令校验、状态提交、领域事件分发 |
| assets/scripts/presentation/ | Cocos 场景、动画、输入、HUD、音效与资源池 |
| assets/scripts/platform/ | 浏览器与微信的存储、生命周期、资源接口 |
| assets/config/ | 角色、物品、配方、掉落、季节、夜袭和成长配置 |
| assets/scenes/、assets/prefabs/ | 启动、菜单、世界和可复用表现对象 |
| tests/domain/、tests/integration/ | 无编辑器规则测试和适配集成测试 |
| docs/ | 工具链说明、开发启动、人工验收与性能报告 |

引擎工程的 settings、profiles 等按选定版本规范生成，资源必须保留对应 meta；不手写猜测场景格式。使用 Vitest 或经所选 Node 验证的等价轻量测试运行器运行领域规则，不引入前端页面框架。

### 2. 统一模拟与事件优先级

领域规则以固定 30 Hz 初值更新，画面按设备刷新插值；前台单帧真实时间增量和追赶次数设上限，避免恢复时补算巨量时间。后台、背包／制造管理界面及系统暂停采用统一暂停原因集合，只有所有暂停原因解除才继续。管理菜单暂停只冻结模拟推进，允许经过独立校验的背包装备与制造命令完成事务；切后台和终局禁止这些命令。建造放置与维修属于世界操作，时间继续；死亡倒计时不自动暂停。

同一 tick 顺序：输入意图与前置条件 → 移动／AI／攻击 → 汇总伤害和状态 → 塔终局判定 → 角色死亡与奖励事务 → 未终局时复活及迁塔提交 → 事件与存档。所有提交再检查终局标志。塔死亡同 tick 优先于复活、制造交付及迁塔，避免最后一帧救活已毁世界。

状态包含 runStatus（running／game-over）、playerLife（alive／respawning）、pauseReasons、relocation（idle／channeling）。不用多个独立布尔值组合出“已终局但还能复活”的非法状态。

### 3. 有限世界、表现排序与碰撞

初值为 128×128 格地图、16×16 格区块，先用经过校验的固定布局加种子化资源摆放，再评估更复杂的程序生成。出生安全区保证塔、木石食物和首夜必需路线；地图生成后做连通性校验。有限矿藏数量必须覆盖首版进阶路线，不能因基础地图生成导致必需配方永远不可达。

地面可使用 Tiled 编辑与静态装饰，动态树木、矿点、掉落和建筑采用领域实体。持久化状态与显示节点完全分离；节点卸载不会删除世界实体。人物和大型物体按脚底 Y 值排序，HUD 独立层。原型使用四方向序列帧与占位素材，正式画风和素材来源在美术阶段评审。

网格负责静态阻挡、建造占位和寻路；移动采用圆形角色与邻近障碍的扫掠／滑动判定，战斗用扇形、圆形和矩形范围。Builtin 触发检测可用于表现接触，不能依赖其自动做刚体阻挡。先不启用 Box2D；若原型无法满足击退需求，再以实测结果评估，避免首版承担不必要的刚体成本。

只激活玩家周围区块与塔周围防守区块的并集，二者重叠时实体只更新一次。远处资源按游戏时钟补算；离开视野不能冻结塔。对已生成且影响本局的敌人保存位置、生命和必要 AI 状态；运行中暂离活动区域的夜袭单位仍需维护推进，不因卸载节点而销毁或复制。

### 4. 昼夜、四季与内容下限

所有系统依赖同一个游戏时钟。初始平衡表如下，均可调整，不是用户不可变更的指定数值：

| 参数 | 原型初值 |
| --- | --- |
| 春夏秋一日 | 白天 360 秒、黄昏 60 秒、黑夜 180 秒 |
| 冬季一日 | 白天 300 秒、黄昏 60 秒、黑夜 240 秒 |
| 每季 | 7 个游戏日，春季开局；第 28 天结束进入第二年春季 |
| 战斗等级／采集等级上限 | 20／各 10，曲线配置化 |
| 额外技能学习资格 | 角色 3、6 级各开放一个名额，塔旁训练并消耗配置材料 |
| 单件死亡永久丢失率 | 0.20，所有稀有度相同，五槽独立 |
| 复活 | 8 秒，恢复满生命与体力，2 秒保护；饥饿至少恢复至 25%，温度回安全范围，避免死亡循环 |
| 迁塔 | 8 秒引导、60 秒冷却、消耗配置木石；仅白天，开始和提交双重校验 |

生命、体力、饥饿先实现，温度在四季阶段启用。首版基础食物、药材、木石材料必须足够支撑恢复。温度通过季节基础值、装备和篝火等设施修正，先不做复杂天气模拟、火灾蔓延或农场生态。

四季至少各有一项资源差异、一种特色敌人变体或精英事件及关键材料。春季丰富基础资源，夏季高温与耐热材料，秋季偏食物储备与重装敌人，冬季低温、较少食物与长夜。每季末设置一次精英／首领事件；首版首领是独立可验证的事件，不以巨大内容量为前提。击败首领不是世界自动结束条件。

黑夜的野外狂暴是单层状态，由基础配置派生属性，不能每次加载叠乘。夜袭敌人有独立来源标记，黎明停止生成并撤退清理，不发清理奖励；野外怪物解除狂暴继续存在，避免删掉全部野外生态。

### 5. 战斗与两角色

动作采用显式状态：idle／move／attack／block／blink／cast／dead。平 A 具有前摇、命中窗口、后摇，使用 attackId + targetId 去重；格挡按朝向与角度判断，持续格挡消耗体力、抑制体力恢复，完美格挡窗口配置化。闪现视为沿路径的短距离位移，截断到最后合法位置；无位移不消耗冷却。成功闪现可配置短暂闪避窗口，但不允许穿过墙体。

林地守望者用效率与维修消耗系数实现天赋；荒野猎手用“完美格挡后一次强化攻击”和“成功闪现后限时战斗增益”实现差异，所有加成经过统一属性计算，重复通知不叠加。角色选定后本局固定。

横扫、冲击波、战吼、急救四选二，通过训练在本局最多学习两种，学习前明确提示本局不可改选。战吼只在有限范围和持续时间影响仇恨，不能全地图永久吸走塔仇恨。急救检查并消耗药材。复活保留所学技能及原有冷却，死亡不能刷新大招。

### 6. 装备、经济和成长

用 EquipmentDefinition 描述模板，EquipmentInstance 保存实例 ID、模板 ID、部位、阶级、稀有度与固定效果；背包用堆叠材料及非堆叠装备实例。第一版无随机词条与装备耐久，防止同时叠加永久丢失和额外维修负担。采集工具使用独立工具物品，不能混入五个可穿戴装备槽。

完整首版至少有五部位×四稀有度的 20 个可获得装备模板。武器原型先做单一近战基础动作，通过数值与效果变化区分，不为每把武器重做动画。白蓝由制造和普通怪物低概率掉落获得；紫金以采集材料与精英／季节首领稀有材料混合制造。每种关键材料提供来源说明，稀有材料以击杀次数保底或可累计碎片保证长期可达。保底计数独立持久化。

配方事务在开始时检查材料、设施、空间与状态，在同一领域提交中扣料并产生实例；未提交不能先扣一半。拆解要求装备已在背包，按 instanceId 消耗。应急武器使用同一唯一性规则，不可拆解，可占正常武器槽且死亡时也遵循该槽判定；丢失后再领取仍无材料收益。

战斗经验只随有效死亡结算一次，等级解锁两个训练名额并增加基础能力。采集经验按实际交付资源增加，三条曲线独立；进阶收益以效率和权限为主。敌人强度主要由天数、季节和区域定义，不实时镜像角色等级。

### 7. 防线、夜袭与迁塔

用网格占位和局部导航版本管理树木、塔、墙和门。放置、拆除、开关门、墙倒塌只失效相关区域路径。A* 寻路先以可通行空间规划；没有直接路线时，用含可破坏墙的代价图选定突破方向，再选攻击者能实际到达的墙边攻击格。路径重算限频，堵塞时重试或重选，不能每怪每帧全图寻路。怪物之间采用轻量分离和墙边攻击位预约，不将怪物自身作为永久静态墙。

敌人至少包含近战、快速和攻城类型。近战可被附近玩家吸引，攻城优先威胁防线与塔；仇恨有距离和时长限制，确保绕圈不能永久卸掉营地压力。夜袭从塔外围已验证可生成区域进场，不直接在玩家、墙内或塔身生成。地图边缘缺少合法出生点时选择其他方向并回退到合法外围，不能无限循环生成搜索。

调度器用 nightId、waveId、剩余预算和活动数上限控制规模；原型同屏／活动敌人上限先设 40，再依据真机结果调整。黎明统一结束普通夜袭。难度和出生策略读取天数与季节，迁塔不改变预算、不重置精英事件。

迁塔在玩家建造范围内选择已探索且可达的合法落点，允许通过多次迁移逐渐深入地图；不是全图瞬移。开始不删除旧塔，channeling 期间旧塔可受伤；提交保留最新血量，重新校验阶段、空间、敌人、材料、角色及塔状态，然后原子替换位置与复活锚点。黄昏到来或受击取消，不扣材料；冷却从成功提交开始。围墙和其他设施不会随塔搬迁。夜间允许修墙但禁止修塔，白天修塔也需要材料与时间。

### 8. 死亡、随机与保存

角色生命归零后创建 deathId 与五槽穿戴快照。按固定部位顺序对每个非空槽分别取随机数，r < lossProbability 时永久删除指定实例并重算属性，生成损失记录、复活截止游戏时刻。空槽不消耗抽取；背包物品不抽取。测试覆盖概率 0、1 和可控随机序列，不用概率统计测试替代规则验证。

游戏使用可保存状态的伪随机源；地图、掉落、死亡至少分流，避免视觉特效或地图加载消耗死亡随机序列。领域事务持有唯一 ID，写入提交后的随机状态和结果，恢复时读取结果而非重新抽取。不承诺跨引擎物理的逐帧确定性，仅约束领域状态与已经提交的随机结果。

存储通过 StoragePort 区分浏览器开发适配与微信本地文件适配。快照包括版本、配置版本、runId、tick、角色／物品／世界／建筑／敌人／夜袭、保底与随机状态。采用两个带序号和校验的快照槽，加带序号的关键事件日志；先写入并读回校验新内容，再提升有效序号并保留上一有效快照。恢复读取最高有效快照并按序重放其后的完整关键事务；损坏尾部忽略并提示，不静默清空。定期压缩日志，限制大小并只保留去重所需记录。

死亡永久损失、塔终局、制造和迁塔在继续可交互前提交关键记录，I/O 失败暂停并提供重试，不让玩家重掷结果。击杀奖励的领域去重与保存顺序一致。正常周期与切后台创建快照；不能依赖 onHide 一定执行完毕，强杀可能回退到最近成功提交点，界面和文档说明这一边界。本地文件可被用户改动，不将此设计描述为防作弊方案。

重放时事务携带对应物品、材料、实体变化与随机后状态，按事务 ID 幂等应用；不是从旧敌人状态单独重放一笔奖励。迁塔中断恢复时取消未提交引导、保留原塔；已完成迁移恢复新位置。死亡倒计时按游戏时钟继续，终局存档不能继续成活局。

### 9. 分阶段内容与验收

| 阶段 | 交付 | 门槛 |
| --- | --- | --- |
| 1 | 工程、平台接口、移动、平 A／闪现／格挡、一个敌人和碰撞 | 微信真机战斗与基础操作可验证 |
| 2 | 木石食物、背包、基础配方、塔、木墙、首夜、死亡损失与复活、基础完整存档 | 能连续玩过首夜，迁塔和塔终局可演示 |
| 3 | 两角色天赋、角色与三采集成长、白蓝装备、四选二技能训练 | 两种角色均能完成起步，死亡保留成长 |
| 4 | 木石强化墙、三敌人、破墙策略、维修、20 模板与紫金材料路线 | 封闭营地仍可进攻，所有配方可达 |
| 5 | 四季、温度设施、四种季节变体／事件、季末精英 | 加速规则测试与正常速度抽样共同覆盖完整一年 |
| 6 | 教程、美术音效、性能、存档兼容、设备验证 | 完整规格逐项验收，无未声明的缺项 |

首个试玩版只要求阶段 1～2，但完整变更完成需要全部阶段。不要把未实现内容标为完成，也不在发现已有代码后重复建工程。

### 10. 验证与性能预算

规则测试覆盖五槽独立损失、死亡幂等、终局优先、配方交易、经验溢出、资源刷新、季节边界、动态寻路、迁塔失败和恢复；通过可控时钟／随机／存储故障注入保证可复现。集成测试覆盖暂停原因叠加、切后台、损坏快照恢复、日志重放与资源失败。

验收以 specs/ 场景为来源，自动化验证数据正确性；玩家操作、画风、黑夜辨识度与防守节奏由用户真机试玩确认。首版验收目标为选定 Android 与 iPhone 各一台，在配置的 40 活动敌人场景稳定达到 30 FPS 目标、连续 30 分钟无崩溃且内存无持续无界增长；记录具体设备、微信版本、引擎版本、加载耗时、峰值内存、帧率和采样方式。上述是待实测目标，不是当前已达成结果。先设设备基线，再按测量优化，不能声称覆盖全部低端机。

资源按启动、通用世界、角色、怪物和季节划分 Bundle，显式加载和释放共享依赖；纹理图集、对象池、视野裁剪和限频 AI 优先于复杂底层优化。普通模式与采用的 iOS 高性能模式分别测，不能混用结果。无实测必要不增加 worker、复杂 ECS 或大物理库。

## Risks / Trade-offs

- [怪物卡墙／所有怪物每帧寻路] → 将封闭、狭路、墙倒塌与地图边缘作为规则回归场景，限制重算并预约攻击位置。
- [装备永久损失造成连续失败] → 使用可调整的 20% 初值、清晰风险说明、应急武器和可持续基础材料；不给死亡提供可拆解收益。
- [等级与装备增长使夜袭失去意义] → 日数／季节独立控制威胁、限制属性乘算、逐阶段试玩，不直接镜像玩家等级。
- [迁塔回血、复制塔或逃避难度] → 双重校验、单次原子提交、保留最新血量与波次，夜间锁定。
- [存档部分提交导致物品丢失或重掷] → 事务 ID、完整结果、随机后状态、双槽及故障恢复测试；不覆盖唯一有效文件。
- [后台补时直接死亡、iOS 内存异常退出] → 统一暂停、重置 delta、分包和真实设备测量。
- [美术工作量超出程序工作量] → 先四方向占位和受控内容量，按许可清晰的素材替换；装备首版不强制全套换装外观。
- [首晚原型被误认为完整首版] → 分阶段验收与任务清单保持全部功能范围，最终按九份规格验收。

## Migration Plan

当前没有旧游戏或生产数据需要迁移。实施从空工程到测试小游戏包，先浏览器规则验证、再开发者工具、最后真机，不在本提案阶段上传或覆盖部署。

首个存档使用 schemaVersion=1；未来版本显式迁移并保留原备份。回退构建前检查存档版本，不支持的版本只提示并保留数据。发布前保留上一可用构建、配置与测试记录，回退不靠清除玩家存档。

## Open Questions

- 正式美术风格、音效来源和角色命名：原型采用占位素材，不影响规则或模块边界，正式替换前由用户审阅。
- 平衡初值：死亡率、日长、季长、技能数值、配方成本通过阶段试玩调整；改变已确认规则需要另行修订规格。
